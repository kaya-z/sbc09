# FPGA 版 (Sipeed Tang Nano 9K)

sim09 / sbc09 の「v09」マシン (Level 1: 64KB のフラットメモリ、`$E000` の I/O ページ) を、FPGA ボード
**Sipeed Tang Nano 9K** (Gowin GW1NR-LV9QN88PC6/I5) の上に作ります。シミュレータと同じ ROM・ディスクイメージで、
FUZIX と NitrOS-9 Level 1 が動きます。

> **状態**: 設計全体を Verilator で動かして検証し (下の「検証」)、Gowin IDE で配置配線とタイミング (67.5MHz) を通しています。
> **実機 (Tang Nano 9K) で確認できたもの** (2026-10-11): SRAM への書き込み、PSRAM、microSD (FUZIX のイメージ)、UART。
> FUZIX が起動して `login:` からコマンド (`ls`、`ps`、`df`、パイプ、`date`) と `shutdown` まで動き、NitrOS-9 Level 1 もシェルまで起動します。
> **HDMI の映像と漢字も実機で確認できました** (2026-10-15。LCD に HDMI-DVI ケーブルで**直結**して、起動メッセージ、`login:`、JIS 第 1 水準の漢字、半角カナ、Latin-1)。
> KVM スイッチ経由では映りませんでした (下の「実機での確認」)。
> 実機で見つかったこと (PSRAM のクロック、CPU のタイミング) は「実機での確認」にまとめました。

```
   27MHz ──PLL──▶ 67.5MHz ┬─▶ MC6809 コア (Greg Miller)   E = 67.5MHz/36 = 1.875MHz  ← 4相: E↓ Q↑ E↑ Q↓ が 9 クロックずつ
                         ├─▶ メモリアクセス ──▶ PSRAM コントローラ (Feng Zhou) ──▶ パッケージ内の 64Mbit PSRAM  (RAM 64KB)
                         │                  └─▶ ROM (ブロック RAM, 256B..32KB, 書き込み禁止)
                         ├─▶ ACIA ($E000/1) ── UART 115200 8N1 ──▶ USB シリアル (BL702)   … コンソール
                         ├─▶ タイマ/時計 ($E030-36) 50Hz
                         ├─▶ ディスク ($E040-47) ── SPI ──▶ microSD スロット   … /d0 /d1
                         └─▶ コンソールの出力を横取り ──▶ 文字コードの復号 (UTF-8/EUC-JP/Shift_JIS) ──▶ HDMI 文字画面
                                                        (80x25, 640x480@60Hz, 漢字は PSRAM の字形から) ──▶ HDMI コネクタ
```

## 必要なもの

* Tang Nano 9K と USB ケーブル、microSD カード (SDSC / SDHC / SDXC のどれでも)
* ビルド: Gowin IDE (教育版 V1.9.11.03 で確認、`/usr/local/IDE`)。シミュレーションだけなら Verilator と g++
* 書き込み: `openFPGALoader` (または Gowin Programmer)

## ビルドと書き込み

```sh
fpga/tn9k/scripts/build.sh fuzix     # fuzix | os9 | v09   (第 2 引数は IDE のディレクトリ。既定 /usr/local/IDE)
openFPGALoader -b tangnano9k fpga/tn9k/build/fuzix/impl/pnr/sbc09_fuzix.fs        # SRAM に書く (電源を切ると消える)
openFPGALoader -b tangnano9k -f fpga/tn9k/build/fuzix/impl/pnr/sbc09_fuzix.fs     # フラッシュに書く (電源を入れると起動)
```

`build.sh` は約 1 分で終わります。`HDMI=0 fpga/tn9k/scripts/build.sh fuzix` で HDMI 画面を除いたもの (`sbc09_fuzix_nohdmi.fs`) を作ります。ROM の選び方:

| 引数 | ROM | 置き場所 | 用途 |
|---|---|---|---|
| `fuzix` | `fuzix/images/bootrom.bin` (256 バイト) | `$FF00-$FFFF` | FUZIX (カードの先頭から起動) |
| `os9` | `os9/os9v1.rom` (16KB) | `$C000-$FFFF` | NitrOS-9 Level 1 |
| `os9boot` | `os9/os9v1boot.rom` (8KB) | `$E000-$FFFF` (`$E000-$E0FF` は I/O が優先) | NitrOS-9 Level 1 を**カードから起動**する (下の「OS-9 をカードから起動する」) |
| `v09` | `os9/v09.rom` (32KB) | `$8000-$FFFF` | 参考実装のモニタ (FIRQ のタイマ) |

ビルドした日時が時計の初期値になります (電池がないので、電源を入れるたびにその日時から数え始めます)。
ビルド済みのビットストリーム (`fuzix`、`os9`、`os9boot` は HDMI つき、`fuzix_nohdmi` は HDMI なし。2026-10-15 のビルド、67.5MHz) は `fpga/tn9k/images/` にあります。

```sh
gzip -dc fpga/tn9k/images/sbc09_fuzix.fs.gz > /tmp/sbc09_fuzix.fs && openFPGALoader -b tangnano9k /tmp/sbc09_fuzix.fs
```

## microSD カード

カードは**ファイルシステムなしの生のディスク**として使います。ドライブ 0 はカードの 0 ブロックから、ドライブ 1 は 128MB の位置
(ブロック 262144) からです (`sim09 -0 a.dsk -1 b.dsk` の 2 つのイメージを並べたもの)。

```sh
# FUZIX (4MB のイメージ)。/dev/sdX は必ずカードのデバイスを確かめてから! (間違えるとそのディスクを壊します)
gzip -dc fuzix/images/sim09-fuzix.dsk.gz | sudo dd of=/dev/sdX bs=512 conv=fsync
# NitrOS-9 Level 1: ドライブ 0 と 1
sudo dd if=os9/OS9.dsk  of=/dev/sdX bs=512 conv=fsync
sudo dd if=os9/WORK.dsk of=/dev/sdX bs=512 seek=262144 conv=fsync
```

カードの書き込みは**書き込みのたびにブロックごと (512 バイト) に完了を待つ**ので、止める前の特別な操作は要りません。
ただし FUZIX は `shutdown` で止めてください (ファイルシステムを閉じてから `Halted.` を出し、電源制御レジスタ `$E00F` に
`$A5` を書くと LED5 が点いて CPU が止まります)。

## OS-9 をカードから起動する

`os9` の ROM は OS 全体 (16KB) を持っていますが、`os9boot` の ROM (8KB) は**カーネル (`Krn`、`KrnP2`)、`Init`、ブートモジュール `Boot`、`IOMan`、`SCF`** だけを持ちます。
本物の OS-9 Level 1 と同じように、`Boot` が**カードのドライブ 0 の起動ファイル `OS9Boot`** を RAM に読み込み、そこにある `RBF`、ドライバ (`PDisk`)、
ディスクとコンソールの記述子、`Clock`、`Shell`、`SysGo` などをカーネルが使います (`mdir` で見ると `Boot` が先頭に出ます)。
ROM を作り直さなくても、ディスクのファイルを入れ替えれば OS の構成を変えられます。
`IOMan` と `SCF` (合計 3.8KB) を ROM に置いたのは、起動ファイルが RAM に占める分を減らして、**`jwp` が動くだけの空きメモリ**を残すためです
(`jwp` は連続した約 174 ページの空きが要ります。`mfree` で、ROM だけの `os9` が 170 ページ、起動ファイルに全部入れると 160 ページで `jwp` は `ERROR #207`、
`IOMan` と `SCF` を ROM に移すと 175 ページで動きます)。実機でも `mfree` が 175 ページで、`jwp` の画面が出ることを確認しました (2026-10-15)。ROM は `$E000` から始まり、I/O のレジスタ (`$E000-$E0FF`) を避けて、最初のモジュールを `$E100` に置きます (`tools/makerom.c`)。

* `Boot` は `os9/level1/boot.asm` (MIT)。LSN 0 の `DD.BT` と `DD.BSZ` から起動ファイルを探して読む部分は NitrOS-9 の `boot_common.asm` をそのまま使い、
  ディスクポート (`$E040`: PDisk と同じ DMA 方式) の読み出しだけを書きました。シミュレータでも同じ ROM で動きます
  (`./sim09 -rom os9/os9v1boot.rom -0 os9/OS9.dsk -v os9/level1`)。
* 起動ファイルは `make -C os9` が作り (`os9/OS9Boot.bin`、6.8KB: ROM にないモジュールを続けたもの)、`tools/mkboot.py` が `os9/OS9.dsk` の `OS9Boot` ファイルの場所に書いて
  `DD.BT`、`DD.BSZ`、ファイルの大きさを更新します (`make -C os9 bootdisk`)。`OS9.dsk` は ROM だけで起動する `os9` でもそのまま使えます (ROM が先に見つかるので、起動ファイルは読まれません)。
* 端末の文字コードは起動ファイルの `term` で決まります (EUC-JP や Shift_JIS にするには、`os9/Makefile` の `BOOTMODS` の `term` を `term_euc` に変えた起動ファイルを `tools/mkboot.py` で別のディスクに入れます)。
* カードは `os9` のときと同じ (`dd if=os9/OS9.dsk of=/dev/sdX ...`)。ドライブ 1 は `os9/WORK.dsk`。
* `fpga/tn9k/scripts/build.sh os9boot` でビットストリームを作ります (`images/sbc09_os9boot.fs.gz`)。起動ファイルがディスクにないと、OS-9 は何も出さずに止まります。
* `make test-fpga` の `os9boot` (2 項目) と `tests/os9_test.py` (2 項目) で確かめています。
* **実機の Tang Nano 9K でも動きます** (2026-10-15。カードに `OS9.dsk` を書いて、電源を入れるだけで `OS9:` まで起動し、`chx /d0/cmds` のあと `mdir` と `dir /d0` を確認。HDMI の画面にも出ます)。
* `OS9.dsk` の `/d0/cmds` には、標準のコマンドに加えて **`dhry` (Dhrystone)、`jwp`、`shutdown`** を入れてあります (FPGA 版には `/v0` がないため)。`chx /d0/cmds` のあと `dhry -t 10` などで動きます。**止めるときは `shutdown`** (電源制御レジスタ `$E00F` に `$A5` を書いて CPU を止める。LED5 が点く。ディスクへの書き込みは 1 ブロックごとに完了を待つので、その前に特別な操作は要らない)。他のコマンドを入れるには、`sim09 -v os9/level1` で `copy /v0/cmds/名前 /d0/cmds/名前` と `attr /d0/cmds/名前 e pe r pr` を実行します (そのあと `python3 tools/mkboot.py` で起動ファイルが残っていることを確かめられます)。

## `jwp` と SKK 辞書 (カード起動の OS-9)

`OS9.dsk` の `/d0/cmds` には `dhry` と `jwp` が入っています。`jwp` は連続した約 174 ページの空きメモリが要るので、**ROM に `IOMan` と `SCF` を持つ `os9boot`** で動かします
(起動ファイルに全部入れた構成では `ERROR #207`。上の「OS-9 をカードから起動する」)。

```
OS9:chx /d0/cmds
OS9:jwp memo.txt           (終了は ^Q、保存は ^S。キー入力は UART、画面は LCD と UART の両方)
```

**SKK の辞書をドライブ 1 (`/d1`) に入れる** (2026-10-15 に実機で確認):

```sh
make skk                                    # os9/skk/SKK_utf8.dsk (約 5.7MB)。SKK-JISYO.L が要る (apt install skkdic)。GPL の辞書から作るので、リポジトリには入れていません
# カードのドライブ 1 の位置 (512 バイトのブロック 262144 = 128MB) へ。/dev/sdX は必ずカードのデバイスを確かめてから!
sudo dd if=os9/skk/SKK_utf8.dsk of=/dev/sdX bs=512 seek=262144 conv=fsync
```

ドライブ 0 (`OS9.dsk`、先頭の 180KB) とは重なりません。`dir /d1` で `skk.dic` が見えれば、辞書は読めています。ドライブ 1 に `WORK.dsk` を置いていたときは、辞書で置き換わります
(同じ位置なので、どちらか一方です)。端末の文字コードが EUC-JP / Shift_JIS のときは、`SKK_euc.dsk` / `SKK_sjis.dsk` を使います。

`jwp` の中で `^J` (かな入力モード)、`Kanji` と打って `Space` で変換、`Enter` で確定です。実機で、`Kanji` + `Space` → 「漢字」、`^S` で保存、`list` で UTF-8 の「漢字」を確認しました
(辞書はカードから、必要な部分だけを探します)。使い方の全体は [JWP.md](JWP.md)。

## 使い方

* **コンソール**: ボードの USB を PC につなぐと USB シリアルが 2 つ見えます (BL702)。2 つめ (多くは `/dev/ttyUSB1` か
  `/dev/ttyACM1`) が FPGA につながっています。`picocom -b 115200 /dev/ttyUSB1` など (8N1、フロー制御なし)。
  受信は 255 文字の FIFO があるので、貼り付けても取りこぼしません。
* **リセット**: ボタン S1 (カードの初期化とメモリの消去からやり直します)。電源を入れたときも同じ手順です。
* **LED** (点灯 = 1):

| LED | 意味 |
|---|---|
| 0 | 生きている (約 5Hz で点滅) |
| 1 | PSRAM が立ち上がり、64KB を消去して、CPU が動いている |
| 2 | カードの初期化が終わった |
| 3 | カードにアクセス中 |
| 4 | カードの初期化に失敗した (カードがない、または応答しない。次のコマンドで初期化をやり直します) |
| 5 | 電源制御 (`$E00F` = `$A5`) で止まった |

起動の手順: リセット → PSRAM の初期化 (約 0.2ms) → 64KB の消去 (約 10ms) → CPU のリセット → ROM が動き、最初のディスクアクセスは
カードの初期化 (数十〜数百 ms) が終わるまで CPU を止めて待ちます。FUZIX は電源を入れてからログインまで約 10 秒かかります (スワップに
カードを使い、コンソールが 115200 bps なので)。

## HDMI 文字画面

コンソールの出力 (ゲストが ACIA に書いた文字) を、ボードの HDMI コネクタに文字画面として出します。**出力だけ**で、入力は USB シリアルです
(キーボードをつなぐ口はありません)。ゲストは何も変えずに動きます。

| 項目 | 内容 |
|---|---|
| 映像 | 640x480、60Hz (画素クロック 25.2MHz)、DVI (TMDS)。音声なし。モニタは 640x480@60 を受け付けるもの |
| 文字 | 80 桁 x 25 行、8x16 ドット、上下に 40 ライン (1 行の高さ 16 ドット x 25 = 400) の黒い余白 |
| 色 | ANSI の 16 色 (黒 赤 緑 黄 青 マゼンタ シアン 白 と、その明るい色)。カーソルは点滅するブロック |
| 文字 ROM | 東雲フォント (Public Domain) の 16 ドット: ASCII (`$20-$7E`)、半角カタカナ (`$A1-$DF`)、Latin-1 (`$A0` `$E0-$FF`)。`scripts/mkfont.py` が `vendor/shinonome/` から `rtl/font8x16.hex` を作ります |
| 端末 | 下の表。`jwp` と FUZIX / OS-9 のシェルに必要な分 |

| 入力 | 動作 |
|---|---|
| 表示できる文字 | カーソルの位置に書いて右へ。行の右端では、**次の文字が来たときに**折り返す (右端で止まる状態を持つ) |
| `CR` `LF` `BS` `TAB` `FF` | 復帰、改行 (領域の下端でスクロール)、1 つ戻る、8 桁ごと、画面を消して左上へ |
| `ESC [ n A B C D` | カーソルの移動 (n の既定は 1) |
| `ESC [ r ; c H` / `f` | カーソルの位置 (1 から) |
| `ESC [ 0/1/2 J` `K` | 画面 / 行の消去 (後ろ、前、全部) |
| `ESC [ n L` `M` | 行の挿入、行の削除 (スクロール領域の中) |
| `ESC [ t ; b r` | スクロール領域 (引数なしで全画面に戻す) |
| `ESC [ ... m` | 属性: `0` 解除 `1` 太字 (明るい色) `7` 反転 `22` `27` `30-37` `40-47` `39` `49` `90-97` |
| `ESC [ s` `u`、`ESC 7` `8` | カーソルの保存、復帰 |
| `ESC D` `E` `M` `c` | 改行 (index)、次の行、逆改行、リセット |

使わない列 (`ESC [ ?` で始まるモードなど) は読み捨てます。日本語は次の「漢字」を見てください。

### 漢字

JIS X 0208 の記号・英数・ひらがな・カタカナ・ギリシャ・キリル (1〜8 区) と**第 1 水準漢字** (16〜47 区) を、16x16 ドットで出します
(東雲フォント、Public Domain。3,760 区点のうち 3,488 字に字形があります)。1 字は 2 桁分の幅です。第 2 水準の漢字、JIS X 0212、4 バイトの UTF-8
(絵文字など) は字形がないので、**〓** (JIS `$222E`) で出します。

| 文字コード | 動作 |
|---|---|
| `raw` | `$80` 以上の 1 バイトは文字ROM の番号 (Shift_JIS の半角カナは `$A1-$DF` のまま出る) |
| UTF-8 | 2 バイトと 3 バイト。ASCII、Latin-1、半角カナ (U+FF61-FF9F) は 8x16 の字形、そのほかは Unicode から字形の番号を引く (PSRAM の表) |
| EUC-JP | `$A1-$FE` の 2 バイト、`$8E` + 半角カナ、`$8F` + 2 バイト (JIS X 0212: 〓) |
| Shift_JIS | `$81-$9F` `$E0-$FC` の 2 バイト、`$A1-$DF` の半角カナ |

* **始めの文字コード**はビルドで決まります (`build.sh` の `fuzix` `os9` は UTF-8、`os9euc` は EUC-JP、`os9sjis` は Shift_JIS、`v09` は raw。環境変数 `HDMI_CHARSET=0..3` で変える)。
* **動いている間の切り替え**: `ESC % G` (UTF-8)、`ESC % E` (EUC-JP)、`ESC % S` (Shift_JIS)、`ESC % @` (raw)。
* 壊れた並び (切れた UTF-8、2 バイト目が違う EUC / Shift_JIS) は `?` を出して、その壊した 1 バイトをもう一度読みます。
* 行の右端に 2 桁の文字が入らないときは、次の行に出します。2 桁の文字の片方に重ねて書くと、残った半分は消えます。

**漢字のイメージ**: 字形 (16x16 で 32 バイト x 3,760) と、UTF-8 のための Unicode → 字形番号の表を、`scripts/mkkanji.py` が 1 つのファイル `kanji.bin`
(185,856 バイト、配置は `rtl/kanji.vh`) にまとめます。**ボードの SPI フラッシュ (1MB の位置)** に書いておくと、電源を入れるたびに FPGA が
PSRAM へ写します (約 0.1 秒)。ビットストリームを SRAM に書くだけのときも、フラッシュの内容は残るので、一度書けば足ります。

```sh
# 漢字データは 1MB の位置。ビットストリーム (0 番地) を -f で書くと**フラッシュ全体が消える**ので、必ず**ビットストリームを書いたあと**に書く
openFPGALoader -b tangnano9k --external-flash -f --verify -o 1048576 fpga/tn9k/images/kanji.bin
```

`--external-flash` が要ります (付けないと `Failed to claim FPGA device: incompatible file format` で止まります)。
書き込みには約 1〜2 分かかります (JTAG 経由で 185KB)。
`--dump-flash` (読み戻し) はこの版の openFPGALoader (0.10.0) の Gowin では使えないので、`--verify` で確かめます。
書き込みの間に FPGA の SRAM の設計は消えます (あとでビットストリームをもう一度書き込みます)。

フラッシュにイメージがないときは (先頭が `KJF1` でないとき)、写さずに起動します。漢字は〓で出ます (半角の文字は出ます)。

仕組み (`hdmi_decode.v` `hdmi_glyph.v` `psram_arb.v` `psram_xfer.v` `kanji_loader.v`): 復号器 (画素クロック) がバイトを 8x16 の文字か 16x16 の字形番号にし、
UTF-8 は `psram_xfer.v` 経由で PSRAM の表を 2 回引きます。画面の 1 セルは `{色 8 ビット, 符号 16 ビット}` で、2 桁の文字は左半分 (`$1000 | 字形番号`) と右半分
(`$2000 | 字形番号`) の 2 セルです。表示は 1 ラインずつ、次のラインに漢字があれば `hdmi_glyph.v` (67.5MHz) が PSRAM からその 1 ラインの 16 ドットを読んでラインバッファに置き、
表示がそれを使います。PSRAM は CPU、ディスク、復号器、字形の読み出しで共有で、`psram_arb.v` が順番に回します (字形の読み出しが最優先: 時間の制約があるため)。起動のあと、PSRAM を 0 で
消してから漢字のイメージを写し (`kanji_loader.v`)、それから CPU のリセットを外します。

回路 (`fpga/tn9k/rtl/hdmi_*.v` `tmds_enc.v`): 端末 (`hdmi_term.v`) が 80x25 の文字と色の VRAM (2 つの複製: 画面用と、スクロールで読む用) を書き、
表示 (`hdmi_video.v`) が VRAM と文字ROM を読んで 1 画素ずつ出し、TMDS エンコーダ (`tmds_enc.v`、8b/10b) が 3 チャンネルの 10 ビットの符号にして、
`hdmi_phy.v` が 126MHz の PLL (27MHz x 14 / 3)、OSER10 (10:1 のシリアライザ)、差動出力 (ELVDS) で送ります。端末も画素クロックで動かして
(67.5MHz の論理だと間に合わない)、ゲストの文字は 67.5MHz から画素クロックへトグルで渡します。画面が追いつかないとき (長いスクロール) は、
CPU を止めて文字を落とさないようにします。

| 資源 (FUZIX) | HDMI なし | HDMI (文字だけ) | HDMI + 漢字 |
|---|---|---|---|
| 論理 (LUT + ALU) | 4,866 (56%) | 約 6,100 (71%) | **6,746 (78%)** 漢字つき (復号器、字形の読み出し、調停、フラッシュの読み出しで約 670 増える) |
| ブロック RAM | 3 / 26 | 10 / 26 | **16 / 26** (VRAM 9 (3 つの複製)、文字ROM 2、ラインバッファ 1、待ち行列ほか) |
| PLL | 1 / 2 | 2 / 2 | 2 / 2 |

タイミング (漢字つき): 67.5MHz の論理は Fmax 72.6MHz (余裕 約 6%。ビルドのたびに `build/ROM/impl/pnr/*_tr_content.html` で確認してください)、画素クロックは 41.8MHz (必要なのは 25.2MHz)。

## クロック

| クロック | 周波数 | 作り方・使うところ |
|---|---|---|
| 水晶 | 27MHz | ボード上。PLL の入力 |
| システムクロック `clk` | **67.5MHz** | PLL 1 (`tn9k_pll.v`: 27MHz × 5 / 2。`FBDIV_SEL 4`、`IDIV_SEL 1`、`ODIV_SEL 8`)。PSRAM、SD カード、UART、タイマ、ディスク、端末以外の論理すべて |
| PSRAM のクロック | 67.5MHz と、90° ずらした 67.5MHz | 同じ PLL。ずらした方を PSRAM のコントローラに渡す |
| **CPU の E** | **1.875MHz** | `clk` を 36 分周 (`PH_DIV = 9` クロックずつ 4 相: E↓、Q↑、E↑、Q↓)。1 バスサイクル = 533ns。Q は E より 1/4 周期進む |
| 画素クロック | 25.2MHz | PLL 2 (`hdmi_phy.v`): 27MHz × 14 / 3 = 126MHz を 5 分周。端末、復号器、画面の表示 (HDMI つきのみ) |
| シリアルクロック | 126MHz | 同じ PLL。OSER10 が 10 ビットを 1 画素の間に送る (TMDS) |
| UART | 115200 baud | `clk` / 586 (`BAUD_DIV`) |
| SD カード | 初期化 263kHz、通常 11.25MHz | `clk` / 256 と `clk` / 6 (SPI モード) |
| タイマ | 50Hz | E サイクルを数える (E の周波数に比例する。`CLK_HZ` と `PH_DIV` から計算) |

**E が 1.875MHz なのは、2MHz の近似ではありません**。シミュレータの既定 (1.8432MHz = 115200 baud の 16 倍) に近づけた値です。E の周期は `clk` の 4 × `PH_DIV` 倍
(4 つの相が同じ長さ) なので、67.5MHz では 4 の倍数の 36 クロックが最も近く (1.8432MHz なら 36.6 クロック)、1.875MHz (+1.7%) になります。
2MHz にするなら 33.75 クロックなので、`clk` を 64MHz か 72MHz にして 32 または 36 クロックにすることになりますが、PSRAM が安定して動く範囲
(54〜74.25MHz で確認、81MHz は誤り) との兼ね合いで、いまは 67.5MHz にしています。

**実効の速さは 1.875MHz より遅くなります**。PSRAM の読み出しは 15〜20 クロックかかり、E の半周期 (18 クロック) の中に収まらないことがあります。
そのとき、CPU の E を止めて待ちます (さらに読んだ値が ALU を通り抜ける時間として 6 クロック待つ。「設計」の `settle`)。シミュレーション
(FUZIX の起動後の 20M クロック = 0.3 秒。`fpga/tn9k/sim` の `Vsim_top -h 開始クロック`) で測ると、バスサイクルあたりのクロック数は次のとおりです。

| サイクル | クロック数 | 割合 |
|---|---|---|
| ROM の読み出し、I/O の読み出し、アクセスなし (`VMA`=0) | 36 (止まらない) | 約 24% |
| RAM の読み出し | 47 (+11) | 約 68% |
| RAM の書き込み | 42 (+6) | 約 8% |
| コンソールへの文字の書き込み ($E001) | 約 3700 (UART の 1 文字 = 5860 クロックの待ち) | 約 0.3% |

コンソールへの出力を除くと平均は 43.9 クロック = **約 1.54MHz** (シミュレータの 1.8432MHz の約 83%)、出力が多い区間では 1.2MHz 前後です。
UART の 115200 baud が出力の上限になるので、画面の更新が多いアプリ (`jwp` など) では CPU の速さより出力の速さが効きます。
E の周波数を上げるには `PH_DIV` を小さくしますが、PSRAM の読み出しの待ちは変わらないので、速さは周波数に比例しては上がりません。
**E = 2.109MHz の実験** (`PH_DIV=8 HDMI=0 fpga/tn9k/scripts/build.sh fuzix`。結果は `build/fuzix_nohdmi_ph8/`): 実機で FUZIX が起動し、ログイン、`ls`、`date`、`ps`、`df`、`ls /bin | cat`、
`shutdown` まで普通に動きました (E が 12.5% 速い)。シミュレーションで同じように測ると、RAM の読み出しは 45 クロック (+13)、書き込みは 40 (+8) で、コンソール出力を除いた平均は
41.5 クロック = **1.63MHz** (`PH_DIV=9` の 1.54MHz の +6%)。E を 12.5% 上げても実効は 6% しか上がりません (PSRAM の待ちが変わらないため)。
動作確認は起動と数コマンドだけで、長時間の負荷試験はしていません。配置配線のタイミングは違反なしですが、`tn9k.sdc` の E の制約は 1.875MHz のままです (E の経路は 22MHz まで通るので結果は変わりません)。
既定は `PH_DIV=9` のままです。

OS-9 (ROM から動く) では、ROM のサイクルが多い分、FUZIX より速くなります (測っていません)。

## シミュレータとの違い

メモリマップとレジスタはシミュレータ ([README](../README.md) のハードウェア構成) と同じです。違うのは次の点です。

* **`/v0` (VRBF、ホストのディレクトリ) がありません**。`$E040` に `$D1-$DD` を書くとエラー (`$FF`) が返ります。OS-9 の SysGo は
  実行ディレクトリを `/v0/cmds` にするので、最初に `chx /d0/cmds` を打ちます (`OS9.dsk` の `cmds`)。
* **時計**は電池がなく、ビルドした日時から数えます。タイマは E サイクルを数えるので 50Hz は CPU のクロックに追従します。
* **クロック**は E = 1.875MHz (67.5MHz / 36) です。シミュレータの既定 (1.8432MHz) とほぼ同じで、`-clock` のような設定はありません
  (変えるときは `tn9k_cfg.vh` の `PH_DIV` を変えてビルドします)。
* **ACIA** は 6850 風で、状態の bit0 = 受信あり、bit1 = 送信可。割り込みはありません。ゲストが送信可を見ずに書いても、
  送信が追いつくまで CPU を止めるので文字は落ちません (FUZIX のコンソールはこれに頼っています)。
* **FUZIX の `sh` (V7 の Bourne シェル) はコマンドの引数の 8 ビット目を落とします**ので、`echo 日本語` の出力は化けます (tty の入力のエコーと、ファイルの `cat` は大丈夫です)。OS-9 と `jwp` は問題ありません。
* ゲストのコンソール出力は UART と HDMI 画面の**両方**に出ます (画面が追いつかないときは CPU が待ちます)。
* NMI、HALT、DMA 要求は使いません (つながっていません)。
* `$E080-$E1FF` はただの RAM、`$E004-$E07F` のうち使っていないレジスタは、読むとメモリの内容が見え、書いても無視されます。
* PSRAM は電源投入のたびに 0 で消去します (シミュレータの `calloc` と同じ)。

## 設計

| ファイル | 内容 |
|---|---|
| `fpga/tn9k/rtl/tn9k_top.v` `tn9k_pll.v` | ボードの最上位、PLL (27→67.5MHz と 90° ずらした 67.5MHz)、リセット |
| `fpga/tn9k/rtl/sbc09_soc.v` | CPU、バスサイクル、メモリマップ、PSRAM の調停、レジスタ |
| `fpga/tn9k/rtl/acia_uart.v` `timer_rtc.v` `sd_disk.v` | コンソール、タイマと時計、SD カードのディスク |
| `fpga/tn9k/vendor/mc6809/` | Greg Miller の MC6809 コア (BSD-3-Clause)。**1 か所だけ変更**: 割り込み系フリップフロップの電源投入時の値 |
| `fpga/tn9k/vendor/psram/` | Feng Zhou の PSRAM コントローラ (Apache-2.0)。そのまま (パラメータは `tn9k_top.v` で `FREQ` = システムクロック、`LATENCY` = 3。経緯は「実機での確認」) |
| `fpga/tn9k/constraints/` | ピン (`tn9k.cst`) とタイミング (`tn9k.sdc`) |
| `fpga/tn9k/sim/` | Verilator のシミュレーション (`tb.cpp`: UART、SD カード、スクリプト) |

* **CPU のバスサイクル**: コアは MC6809E のように E と Q の 2 つのクロックで動きます。`sbc09_soc.v` は 67.5MHz から
  4 つの相 (E↓、Q↑、E↑、Q↓) を `PH_DIV = 9` クロックずつ作ります。E が立ち上がった直後、アドレス・方向・データ・有効フラグ
  (コアの `AVMA` は**次のサイクル**が有効かどうかなので 1 サイクル遅らせて使う) が安定しているところでアクセスします。
  PSRAM かディスクの処理が終わっていなければ、次の E の立ち下がりを遅らせる (CPU を止める) ので、メモリの速さが結果に
  影響することはありません。通常、PSRAM の読み出し (12〜15 クロック) は E の半周期の中に収まります。
  止めたあとは、読んだ値がコアの ALU (桁上げの連鎖で約 49ns) を通り抜ける時間として 6 クロック (89ns) 待ってから E を落とします
  (`sbc09_soc.v` の `settle`。これを入れるまで、実機では PSRAM から読んだ値を使う `ADDB` が $10 ずれ、FUZIX が起動しませんでした)。
* **RAM**: 64KB はパッケージ内の PSRAM に置きます (ブロック RAM は 52KB しかなく、FUZIX は 64KB を使い切るため)。
* **ディスク**: `$E040` に `$81` (読み) / `$55` (書き) を書くと、カードの 512 バイトのブロックを読み、256 バイトのセクタを DMA で
  PSRAM とやり取りします (書きは読み出して直して書き戻す)。最後に使ったブロックはバッファに残るので、同じブロックの 2 つめの
  セクタは速いです。処理中は CPU を止め、`$E040` を読むと結果 (0 = 正常、`$FF` = 失敗) が見えます。
* **タイミング**: Gowin の配置配線で、67.5MHz の論理は Fmax 約 72〜76MHz、CPU のクロック E は 23MHz (必要なのは
  1.875MHz) で、違反はありません (`build/ROM/impl/pnr/*.tr.html`)。CPU と 67.5MHz の論理は、互いに安定しているときにだけ値を
  やり取りするので、その間のパスは `tn9k.sdc` で「タイミングを見ない」と宣言しています。ただし E の周期 (533ns) まるごとを
  使えるとして解析されるので、データが E の立ち下がりの直前に変わる設計では実機で壊れます (上の `settle`)。
* **資源** (FUZIX、HDMI なし): LUT 56%、レジスタ 19%、ブロック RAM 3/26。

### 実機での確認 (Tang Nano 9K、2026-10-11)

確認できたこと (HDMI なしと HDMI つきの両方のビットストリーム。モニタは未接続):

* **FUZIX**: カードから起動して `login:`、`ls /`、`ps`、`df`、`date` (ビルド時刻から進む)、パイプ、`shutdown` (`Halted.`)。
* **NitrOS-9 Level 1**: ROM からシェルまで起動します (カードに FUZIX のイメージが入っていると `/d0` は読めません。OS-9 用には `os9/OS9.dsk` を書いてください)。
* 命令 66 種の自己検査 (`scripts/mkcputest.py`) の結果が、実機とシミュレーションで一致。

実機で見つかった問題と対処 (同じボードで試すときの注意):

1. **PSRAM は 81MHz では動きません**。コントローラの作者のテスト (`psram_test_top`) も、このボードでは 81MHz で `FAIL. Read wrong data` でした。
   54MHz、67.5MHz、74.25MHz では誤りなしだったので、**67.5MHz** にしました。次の表のとおり、**変えたのは PLL の周波数 (と、それに合わせた `FREQ`) だけ**で、
   位相とラテンシは元のままです。

   | 項目 | 値 | 場所 |
   |---|---|---|
   | PLL の周波数 | 27MHz × 5 / 2 = 67.5MHz (`FBDIV_SEL 4`、`IDIV_SEL 1`、`ODIV_SEL 8`、VCO 540MHz)。元は 81MHz (`FBDIV_SEL 2`、`IDIV_SEL 0`、`ODIV_SEL 8`、VCO 648MHz)。試験した他の設定: 54MHz = (1, 0, 16)、74.25MHz = (10, 3, 8) | `rtl/tn9k_pll.v` |
   | PSRAM クロックの位相 | 90° (`PSDA_SEL "0100"`)、**変更なし**。この位相のまま 54 / 67.5 / 74.25MHz を試した | `rtl/tn9k_pll.v` |
   | `FREQ` (初期化の待ち 150µs の計算に使う) | システムクロックと同じ (`CLK_HZ` = 67,500,000) | `rtl/tn9k_top.v` |
   | `LATENCY` | 3 (**変更なし**。W955D8MBYA は 83MHz まで 3 クロック) | `rtl/tn9k_top.v` |
   | 周波数ごとの試験 | `scripts/psram_scan.sh 名前 FBDIV IDIV ODIV PSDA FREQ`: 作者のテストをその PLL の設定で作って書き込む (`PSRAM_TEST_SRC` に作者のリポジトリの `src/` を指定) | `scripts/psram_scan.sh` |

   81MHz のとき位相やラテンシを変えて直るかは試していません (位相は 90° のまま、周波数だけ下げて直ったため)。
   `scripts/ramtest.s` (PSRAM の全アドレスに数種類のパターンを書いて読む) が UART に結果を出します。
2. **PSRAM から読んだ値を使う `ADDB` が $10 ずれる**: 上の `settle` を参照。見つけるのに使った道具は `scripts/bootcheck.s`
   (カードから読んだカーネルの和を UART に出して `bootcheck_expect.py` と比べる) と、`DEBUG=1` のビルド (UART に PC、レジスタを 31ms ごとに出す `rtl/dbg_uart.v`)。
   シミュレーションでは RTL を零遅延で動かすので、この種の誤りは出ません。
3. **制約ファイルは最後の 1 つしか読まれません** (`.cst`、`.sdc`)。`build.sh` が `tn9k.cst`+`hdmi.cst`、`tn9k.sdc`+`hdmi.sdc` を 1 つにまとめます
   (これを知らずに HDMI つきで LED が全部消えました)。
4. **`openFPGALoader`** (v0.10.0): `ftdi_usb_reset failed (-6)` が出たら USB を抜き差しします。`kanji.bin` をフラッシュへ書くには
   `--external-flash` が要ります (`openFPGALoader -b tangnano9k --external-flash -f --verify -o 1048576 fpga/tn9k/images/kanji.bin`)。
   `--dump-flash` は Gowin では使えません。UART は `/dev/ttyUSB1`、`stty -F /dev/ttyUSB1 115200 raw -echo cs8 -cstopb -parenb -crtscts clocal` で開きます
   (書き込み直後に `[` が並ぶことがありますが、読み捨ててください)。

LED (アクティブロー): LED0 = 点滅 (動作中)、LED1 = PSRAM と起動処理が終わった、LED2 = カードの初期化完了、LED3 = カード動作中、LED4 = カードの失敗、LED5 = 電源断 (`$E00F`)。

**HDMI の映像が映らなかった原因は KVM スイッチでした** (2026-10-15)。三菱 RDT203WM-S (1680x1050 の DVI-D 入力、HDMI-DVI ケーブル) に **KVM スイッチ経由**でつなぐと、
このプロジェクトのビットストリームも、Sipeed のサンプル (`TangNano-9K-example/hdmi` を同じ IDE でビルドしたテストカード) も映りませんでした
(「No Signal」のあとスタンバイ)。**LCD に直結**すると、Sipeed のサンプルも、このプロジェクトの画面も映りました。それまでに試した次のことは、どれも効果がありませんでした
(原因は信号ではなく、経路の途中の機器でした): 画素クロックを分周器ではなく `OSER10` で作る (位相 2 通り)、1280x720@60、出力ドライブ 16mA、差動の極性の反転。
モニタの EDID には 640x480@60 (25.175MHz) と 1280x720@60 が載っていて (水平 31〜82kHz、垂直 56〜76Hz)、出した信号のタイミングは範囲内でした。
**HDMI を使うときは、モニタに直結してください**。

**漢字が出なかった原因 (2 つ)**:

5. **ビットストリームを `-f` でフラッシュに書くと、フラッシュ全体が消えます**。1MB の位置の漢字データも消えるので、書く順番は**ビットストリーム → 漢字データ**です
   (逆にすると、起動時に先頭が `0xFF` で、漢字は □ になります)。
6. **`hdmi_text.v` で、信号 `kanji_ok_p` を宣言する前にポート接続で使っていました**。Verilator は同じコードを正しく動かしますが、Gowin の合成ツールは暗黙の信号を作って、
   あとの宣言をドライバなしにし (ログに `Net 'kanji_ok_p' does not have a driver`)、デコーダには「漢字データなし」(常に 0) が見えて、漢字が □ になりました。宣言を前に出して直しました。
   `build.sh` は、ビルドの最後に、合成ログの `Undeclared symbol` と `does not have a driver` (PSRAM の未使用の出力を除く) を表示します。
7. 漢字ローダのフラッシュの読み出しは、実機で**ときどき失敗しました** (先頭が `0xFF` や別の値)。読む前にフラッシュを初期状態に戻す手順 (`FFh FFh`: 連続読み出しモードの解除、`ABh`: 電源断の解除、
   `66h 99h`: リセット) を入れ、先頭の `KJF1` が違えば最大 8 回やり直します (`rtl/kanji_loader.v`)。

診断用のビルド (UART に、通常の出力のかわりに状態を出す。CPU のレジスタのあとの最後の 4 桁が `status`): `DEBUG=1` はシステムの状態、`DEBUG=2` は漢字ローダ
(`ok`、`done`、失敗した回数、フラッシュから読んだ最初のバイト。正常なら `C04B`)、`DEBUG=3` は `DEBUG=2` でフラッシュの 0x16 番地 (ビットストリーム内の `0xA5`) を読む、
`DEBUG=4` は漢字ローダの `ok` と、デコーダの字形の検索の答え。
